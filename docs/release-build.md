# Release Build (Android)

How to produce a real, signed release APK from this project - keystore
generation, the `key.properties` file `android/app/build.gradle.kts` reads,
and the exact build command. See [deployment.md](deployment.md) for
pointing that build at a deployed API instead of `localhost`.

---

## 1. Generate a keystore (once)

This is the file that identifies *you* as the app's publisher. Every future
update must be signed with the same one - losing it means you can never
publish an update to an app already installed from it, only a new listing.

```bash
keytool -genkey -v -keystore hear_speak_together.jks -keyalg RSA -keysize 2048 -validity 10000 -alias hear_speak_together
```

`keytool` ships with the JDK (the one bundled with Android Studio works:
`"C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe"` on Windows).
It will ask for a store password, your details, and a key password - write
both passwords down somewhere real. **Do not commit this file.** Store it
outside the repository entirely (a password manager's file storage, or an
encrypted drive) - `android/.gitignore` already excludes `*.jks`/`*.keystore`
as a second line of defence, but the file should never be *near* the repo.

## 2. Point the build at it

```bash
cd mobile/android
cp key.properties.example key.properties
```

Edit `key.properties`:

```properties
storePassword=<the store password you set>
keyPassword=<the key password you set>
keyAlias=hear_speak_together
storeFile=/absolute/path/to/hear_speak_together.jks
```

`key.properties` is git-ignored - it will never show up in `git status`,
and that is correct. `build.gradle.kts` reads it at build time and signs
the `release` build type with it; if the file is missing, the build falls
back to debug signing automatically (so a fresh checkout without a
keystore still builds - just not with a distributable signature).

## 3. Build

```bash
cd mobile
flutter build apk --release --dart-define=API_BASE_URL=https://your-api-host/api
```

Output: `mobile/build/app/outputs/flutter-apk/app-release.apk`.

For the Play Store specifically, build an app bundle instead:

```bash
flutter build appbundle --release --dart-define=API_BASE_URL=https://your-api-host/api
```

## 4. Verify the signature

```bash
"$ANDROID_HOME/build-tools/<version>/apksigner" verify --print-certs mobile/build/app/outputs/flutter-apk/app-release.apk
```

Confirms the APK is actually signed with your release key, not the debug
fallback - worth checking once, since a debug-signed "release" build
installs and runs fine, right up until you try to publish an update.

## What's already set up

- **App name**: "Hear & Speak Together" in `AndroidManifest.xml`'s
  `android:label` and `ios/Runner/Info.plist`'s `CFBundleDisplayName`.
- **Package / application ID**: `my.fyp.hear_speak_together` in
  `android/app/build.gradle.kts` - a real identifier, not the
  `com.example.*` placeholder Flutter's template ships with. Changing it
  after a first Play Store upload is not possible, so this should only be
  touched deliberately.
- **Version**: `pubspec.yaml`'s `version: 1.0.0+1` (`versionName` +
  `versionCode` on Android, `CFBundleShortVersionString` +
  `CFBundleVersion` on iOS - Flutter derives both automatically). Bump the
  number after the `+` for every build you upload to a store, even for the
  same `1.0.0`; stores reject a re-upload of a `versionCode` they have
  already seen.
- **Icons and splash screen**: generated by `flutter_launcher_icons` and
  `flutter_native_splash` from `assets/icon/` - see
  `flutter_launcher_icons.yaml` / `flutter_native_splash.yaml`. Regenerate
  after changing the source images:
  ```bash
  dart run flutter_launcher_icons
  dart run flutter_native_splash:create
  ```

## Verified

`flutter build apk --release` has actually been run against this project
(not just `flutter analyze`/`flutter test`, which don't reach Gradle at
all) and produces `app-release.apk` (~56MB unshrunk). Getting there needed
three real, pre-existing gaps fixed in `android/app/build.gradle.kts` and
`android/settings.gradle.kts` - each only surfaces at actual Gradle build
time, never from Dart-side tooling:

- `minSdk` raised from Flutter's default (21) to **24**: `record` (the
  microphone plugin) requires 23, `flutter_tts` requires 24. Gradle's
  manifest merger refuses to build below either.
- `compileSdk` raised to **36** and `ndkVersion` pinned to
  `27.0.12077973`: several plugins (`flutter_tts`, `connectivity_plus`,
  `permission_handler_android`, `record_android`, and others) declare a
  requirement above Flutter's own bundled defaults.
- The Kotlin Gradle plugin bumped from **1.8.22 to 2.1.0** in
  `settings.gradle.kts`: `flutter_tts` 4.2.5 ships Kotlin metadata newer
  than 1.8.22's compiler can read, which fails with "Class 'kotlin.Unit'
  was compiled with an incompatible version of Kotlin."

With no `key.properties` present, the build correctly falls back to debug
signing (confirmed with `apksigner verify` - `CN=Android Debug`). Generate
a real keystore via steps 1-2 above before distributing an APK.

## Future: code shrinking

`isMinifyEnabled`/R8 is deliberately left off in `build.gradle.kts` for
now. Several plugins here use reflection at runtime (`flutter_secure_storage`
reaching the Android Keystore, `permission_handler`'s permission lookups),
and R8 can strip code those calls need unless the right `proguard-rules.pro`
keep rules are in place - the kind of break that only shows up on a real
installed device, not in `flutter analyze`/`flutter test`. Enable it only
after building a minified release APK and manually re-testing sign-in,
microphone permission, and practice end-to-end on a device.
